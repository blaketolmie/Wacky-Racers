\section{Git}

Your group leader should fork the Wacky Racers project template.  This
creates your own group copy of the project on the eng-git server that
you can modify, add members, etc.

Each group member then clones the group project.


\subsection{Project forking}
\label{project-forking}

The template software is hosted on the eng-git GitLab server. To fork the
template, \emph{one} member of your group must perform the following:
\begin{enumerate}
\item
  Go to \url{https://eng-git.canterbury.ac.nz/wacky-racers/wacky-racers}.
\item
  Click the `Fork' button. Under the `Select a namespace' dropdown, select your
  username. Under the `Visibility level' heading, select `Private'. Then click
  `Fork project'. This will create a copy of the main repository for the
  project.
\item
  From the left-hand sidebar on your forked repository's front page, navigate to
  `Manage'~\textrightarrow~`Members' and invite your group members to be project
  Maintainers.
\end{enumerate}


\subsection{Project cloning}
\label{project-cloning}

Once your project has been forked from the template project, each group
member needs to clone it. This makes a local copy of your project on
your computer.

If you are using an ECE computer, it is advised that you clone the
project to your OneDrive instead of the \file{P:} drive (i.e. the `My
Documents' folder). This will make git operations and compilation
100 times faster than using the \file{P:} drive.

There are two ways to clone the project. If you are impatient and do not
mind having to enter a username and password for every git pull and push
operation use:
%
\begin{minted}[breaklines]{bash}
$ git clone https://eng-git.canterbury.ac.nz/groupleader-userid/wacky-racers.git
\end{minted}

Otherwise, set up \program{ssh-keys} and use:
%
\begin{minted}[breaklines]{bash}
$ git clone git@eng-git.canterbury.ac.nz:groupleader-userid/wacky-racers.git
\end{minted}

You can have several different cloned copies of your project in
different directories. Sometimes if you feel that the world,
and \program{git} in particular, is against you, clone a new copy,
using:
%
\begin{minted}[breaklines]{bash}
$ git clone https://eng-git.canterbury.ac.nz/groupleader-userid/wacky-racers.git wacky-racers-new
\end{minted}


\section{Toolchain}
\label{toolchain}

The toolchain comprises the compiler, linker, debugger, C-libraries,
and OpenOCD.

The toolchain can be downloaded for Windows, Linux, and macOS from
\url{https://developer.arm.com/downloads/-/arm-gnu-toolchain-downloads}. For
Linux and macOS, however, it is better to install the toolchain using your
system's package manager: see the instructions in the following subsections.

The remainder of this section provides instructions for installing the
toolchain on your personal computer. If you are using the computers in
the ESL and CAE, then the toolchain is already installed on both Windows
and Linux.  If there is a problem ask the technical staff.

\textbf{Note:} if using the ECE machines, I recommend using Windows and
cloning your project to OneDrive, as unfortunately the filesystem on the
Linux installations on the lab machines is very slow.


\subsection{Toolchain for Windows}

A disclaimer: getting the toolchain to work on your personal Windows machine
can be a little tricky, so we recommend using Linux (using a virtual machine
or dual-booting) or using Windows on the ESL machines. The TAs may have
limited ability to help you debug toolchain issues on your own Windows
machine.

There are two ways to use the toolchain on Windows without a virtual machine:
\begin{enumerate}
  \item Copy the toolchain from the ESL machines (recommended)
  \item Manually install the toolchain
\end{enumerate}

Because this guide is written with Linux in mind, some commands may be
different on Windows. See Section~\ref{esl-windows} for tips on translating
the commands.

\subsubsection{Option 1: copying the ESL toolchain}

The fastest way to get the toolchain is to just copy the
\file{C:\textbackslash{}ence461} directory from one of the ESL machines onto
yours using a USB flash drive, for example. Then you can setup the toolchain
environment by running
\file{C:\textbackslash{}path\textbackslash{}to\textbackslash{}ence461\textbackslash{}ence461-path}
as described in Section~\ref{esl-windows}. (I recommend copying the folder to
the same location as on the ESL machines, i.e. \file{C:\textbackslash{}ence461},
since this will work out-of-the-box with the provided VS Code configuration.)

You will also need to install the
\href{https://www.st.com/en/development-tools/stsw-link009.html}{ST-Link/V2
driver}.

\subsubsection{Option 2: manual installation}

Download the latest ARM toolchain (the file ending in
\code{*-mingw-w64-i686-arm-none-eabi.exe}) from the ARM website link
provided above and run the installer. When the installer completes, make sure
the box labelled `Add path to environment variable' is checked before closing.

Install MSYS2 by following the instructions at \url{https://www.msys2.org/}
(make sure you update package database as described). Then open `MSYS MSYS2'
from the Start menu and run
\begin{minted}{bash}
    pacman -S make mingw-w64-x86_64-openocd
\end{minted}
to install OpenOCD and make. Close the MSYS window.

Finally, you need to add the MSYS binaries to your systems path, type `path'
into the Start menu and open the option that says `Edit the system environment
variables'. Click on the `Environment Variables\ldots' button; then in the
bottom `System variables' box, double-click on the `Path' variable. Add the
following two paths at the bottom:
\begin{minted}{text}
    C:\msys64\usr\bin
    C:\msys64\mingw64\bin
\end{minted}
Click `Ok' to exit out of all the Control Panel menus.

Open a command prompt and test that you can run the following commands:
\begin{minted}{bash}
    arm-none-eabi-gcc --version
    arm-none-eabi-gdb --version
    openocd --version
    make --version
\end{minted}
If you get a missing \code{python27.dll} error when running GDB, you need to
download and install the \emph{32-bit} version of
\href{https://www.python.org/downloads/release/python-2718/}{Python 2.7}.

Finally, install the ST-Link driver as described previously.

\subsection{Toolchain for Linux}

First, if using Ubuntu or Mint, ensure the latest versions are
downloaded:
%
\begin{minted}{bash}
$ sudo apt update && sudo apt upgrade
\end{minted}

Then, install the compiler:
%
\begin{minted}{bash}
$ sudo apt install gcc-arm-none-eabi
\end{minted}

Install the C and C++ libraries:
%
\begin{minted}{bash}
$ sudo apt install libnewlib-arm-none-eabi libstdc++-arm-none-eabi-newlib
\end{minted}

Install the debugger, GDB:
%
\begin{minted}{bash}
$ sudo apt install gdb-multiarch
\end{minted}

Install OpenOCD:
%
\begin{minted}{bash}
$ sudo apt install openocd
\end{minted}

\subsection{Toolchain for macOS}

For macOS machines that have \href{https://brew.sh}{homebrew}
installed, you can use the following command:

\begin{minted}{bash}
$ brew install openocd git
$ brew install --cask gcc-arm-embedded
\end{minted}

(On older versions of homebrew, the second command is
\verb|brew cask install gcc-arm-embedded|.)


\section{Visual Studio Code}
\label{vs-code}

I am content with using the command-line and emacs as a text editor but
I guess that you are not.  If you want bells and whistles, I suggest
using Visual Studio Code, which is installed on the ESL machines.  While
it is written by Microsoft, it is free and runs on Windows, Linux and
macOS. Go to \url{https://code.visualstudio.com/download} and follow the
instructions for your OS to get the latest version.

This project has been configured for VS Code on the ESL computers (but
it's relatively easy to modify it to work on a home computer, be it
Windows, Linux, or Mac). For the simplest use, simply go \code{File ->
Open Folder} and point it at the wacky-racers repository. The project
build settings are configured inside the \code{.vscode} directory.

The compilation and debugging requires the installation of three VS Code
extensions:
\begin{enumerate}
\item C/C++ (Microsoft)
\item Native Debug (Web Freak)
\item Command Variable (rioj7)
\end{enumerate}
VS Code should automatically prompt you to install these the first time
you open the \verb|wacky-racers| directory.

Before running any of the build commands, the \code{BOARD} configuration
variable must be set. In VS Code this is done by choosing your C++
configuration (bottom right of the window) which by default will be
either \code{hat} or \code{racer} (\reffig{vscode-config}).

\begin{figure}
\centering
\includegraphics{figs/vscode-config.png}
\caption{Selecting the board type in VS Code.}
\label{fig:vscode-config}
\end{figure}

The various \code{make} commands for building, flashing, and debugging
can be run from the VS Code UI via the build menu (\code{Ctrl+Shift+B}).
Refer to the `First program' section (Section~\ref{first-program}) to
work out the correct sequence of commands. For example, to build and
upload a program to your board:
\begin{enumerate}
  \item First ensure that you have set the correct build configuration
  (\code{hat} or \code{racer}, see above).
  \item Open the C file of the program you want to build (e.g.
  \code{ledflash1.c}). (You can quickly navigate to files in the
  workspace by pressing \code{Ctrl+P} and typing the name of the file
  you want to open.)
  \item Press \code{Ctrl+Shift+B} to open the build menu
  (\reffig{vscode-build-menu}).
  \item Select the \code{Program} build task.
\end{enumerate}

\begin{figure}[htb]
\centering
\includegraphics[width=0.7\textwidth]{figs/vscode-build-menu.png}
\caption{VS Code build menu (accessible via \code{Ctrl+Shift+B}).}
\label{fig:vscode-build-menu}
\end{figure}

Running a task from the build menu (\reffig{vscode-build-menu}) is
equivalent to running that command via \code{make} in the command line.
For example, performing the above is equivalent to running
\code{make program} in the \code{src/test-apps/ledflash1} directory.

Note that the \code{Debug} build task runs the command line debugger. If
you want to use a more modern debugging interface, open the source file
that you want to debug in the editor and press \code{F5} to launch a
debug session.

On Windows, the provided VS Code configuration assumes the toolchain is
located at \file{C:\textbackslash{}ence461}; this can be configured by
changing the value of the \code{windowsToolchainEnvCmd} field in
\code{.vscode/settings.json}.

\section{Using Windows in the ESL} \label{esl-windows}

There are two ways to use the toolchain on the Windows machines in the
ESL: via the command line (Command Prompt) or VS Code. Both methods use
the toolchain directory located at \file{C:\textbackslash{}ence461}.
When using the command line, you need to ensure that the toolchain
directory is added to the current session's environment (so that the
command line interpreter can locate the executables for GCC, openocd,
etc.). The provided VS Code configuration automatically adds the
toolchain directory to the environment. If you are using your own
Windows machine, we recommend copying the toolchain to the same location
(\file{C:\textbackslash{}ence461}) so the instructions in this guide
will work the same.

\subsection{VS Code}

The \code{.vscode} configuration in the upstream wacky-racers repository
is configured specifically to work on the Windows machines in the ESL.
Most \code{make} commands you will read about later in this guide can be
replaced by running the corresponding task from the VS Code build menu
(\code{Ctrl+Shift+B}).

\subsection{Command line}\label{esl-windows/command-line}

Command Prompt (\code{cmd.exe}) is the Windows equivalent of a Unix
shell. To open, press \verb|Windows Key + R|, type \code{cmd}, and
\code{Enter}. Then run
\file{C:\textbackslash{}ence461\textbackslash{}ence461-path} inside the
CMD window to source the toolchain. You can also access CMD from the
integrated terminal in VS Code.

CMD syntax is quite different from that of Unix shells; however, the
shell commands provided in this guide will also work provided you have
run the toolchain batch file and observe the following differences:
\begin{itemize}
\item To change between drives (e.g. \file{C:} and \file{P:}), pass the
\code{/d} switch to the \code{cd} command.
\item Instead of \code{export VARIABLE=value}, use \code{set VARIABLE=value}.
Also you cannot set an environment variable when you run a command, so
\code{BOARD=hat make} won't work; run \code{set BOARD=hat} and \code{make} in
separate commands instead.
\item To run GDB, you must invoke the complete command name
\code{arm-none-eabi-gdb}.
\item In path names, \file{/} is replaced by \file{\textbackslash}
(backslash). In \file{.c}, \file{.h}, and makefiles, however, you
should still use \file{/}.
\end{itemize}

Windows also provides another command line interpreter called
PowerShell (\code{pwsh.exe}). This is a more modern alternative to CMD
but has quite a different syntax to it and Unix shells: for example,
to set an environment variable you need to use \code{$env:BOARD =
"hat"}. On VS Code on Windows, it is likely that PowerShell is set as
the default shell (i.e. the interpreter used when you press
\verb|Ctrl+`|); to change this, open the command palette
(\verb|Ctrl+Shift+P|) and search for
\code{Select Default Shell} and set it to \code{cmd.exe}.
